# How codes work

## TOTP

Most 6-digit two-factor codes are TOTP (RFC 6238). The site and Tottoro hold the same secret and compute the same code from the same time. There is no network communication.

The computation is in `TOTPGenerator`.

1. Divide the seconds since 1970 by the period (usually 30 seconds) to get a counter. The counter goes up by 1 every 30 seconds.
2. Encode the counter as 8 bytes, big-endian, and take its HMAC with the secret. The hash is usually SHA-1; SHA-256 and SHA-512 are also possible. The HMAC is computed with CryptoKit's `HMAC`.
3. Apply dynamic truncation. Use the low 4 bits of the last HMAC byte as an offset, take 4 bytes from there, and drop the top bit to get a 31-bit number.
4. Take that number modulo 10 to the power of the number of digits, and pad it with leading zeros to that many digits.

Steps 2 to 4 are exactly HOTP (RFC 4226). TOTP is HOTP with the time as the counter.

The tests use the test vectors in Appendix B of RFC 6238 (`TOTPGeneratorTests`).

## Secret format

Sites hand out secrets in Base32 (RFC 4648). It uses only 32 characters, A to Z and 2 to 7, so it is easy for people to read out and type. `Base32` ignores letter case, spaces, and `=` padding when reading.

## QR codes that can be imported

### otpauth://

The QR code shown on a site's two-factor setup page. Google Authenticator's Key Uri Format is the de facto standard.

```text
otpauth://totp/GitHub:octocat?secret=JBSWY3DPEHPK3PXP&issuer=GitHub&algorithm=SHA1&digits=6&period=30
```

| Part | Meaning | When omitted |
|---|---|---|
| `totp` | Type. `hotp` (codes that change per use) is not supported | Required |
| `GitHub:octocat` | Label. "issuer:account name" or just "account name" | Required |
| `secret` | Base32 secret | Required |
| `issuer` | Issuer. Takes priority over the issuer in the label | The issuer in the label |
| `algorithm` | `SHA1` / `SHA256` / `SHA512` | `SHA1` |
| `digits` | Number of digits, 6 to 8 | 6 |
| `period` | Period in seconds | 30 |

Parsing is in `OTPAuthURI`.

### otpauth-migration:// (Google Authenticator)

The QR code shown by "Transfer accounts" in Google Authenticator.

```text
otpauth-migration://offline?data=<Base64>
```

The contents of `data` are protobuf. Google does not publish the format, so Tottoro uses a widely used definition that users reverse-engineered (`google_auth_migration.proto`). The Swift code is generated by the swift-protobuf build plugin on every build, so it is not in the repository.

- With many accounts, the export is split across several QR codes. Each one can be read on its own, so scanning them in order imports everything.
- HOTP accounts are skipped, and the number skipped is shown on screen.
- Google Authenticator does not write the algorithm correctly on export, and the number of digits is sometimes wrong too. Trusting these values makes codes not match. So, like Bitwarden Authenticator, Tottoro always uses SHA-1 and only uses 8 digits when 8 is written. The export format has no field for the period, so the period is always 30 seconds.

Parsing is in `GoogleMigrationParser`.

### Authy

Authy has no official export. To move from Authy, show the QR code again on each site's two-factor setup page and scan it with Tottoro.
